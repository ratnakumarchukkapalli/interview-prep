Concepts & Key Players

What is a Certificate? (The Passport Analogy)

Think of a TLS certificate like a passport. A passport proves who you are, was issued by a trusted authority (government), hasn't expired, and hasn't been tampered with. A TLS certificate does the same for servers and services.

Identity
Who this server is — e.g. rabbitmq.confirmation.svc.cluster.local. Encoded in the Common Name (CN) and Subject Alternative Names (SANs).
Trust
It was signed by a Certificate Authority (CA) that the client already trusts. Without a trusted CA, the client rejects the connection.
Integrity
The CA's cryptographic signature means the cert can't be forged or tampered with. Any modification invalidates the signature.
Expiry
Certificates have a validity period (e.g. 365 days). Expired certs are rejected even if everything else is valid.

End-to-End Certificate Creation Process

Five steps from zero to a working TLS connection. This is what happens under the hood every time you generate certs — whether manually, with cert-manager, or with Istio.

  • 1
    Generate a Private Key

    The private key is the foundation. It never leaves your server. All other steps derive from it.

    bash# Generate 2048-bit RSA private key
openssl genrsa -out server.key 2048

# Or 4096-bit for higher security (slower TLS handshake)
openssl genrsa -out server.key 4096

# Or ECDSA P-256 (faster, equally secure, preferred in modern setups)
openssl ecparam -genkey -name prime256v1 -out server.key
  • 2
    Create a CSR (Certificate Signing Request)

    The CSR bundles your public key + identity info and sends it to the CA. Think of it as filling out the passport application form.

    bash# Basic CSR — CN = the primary hostname
openssl req -new -key server.key -out server.csr \
  -subj "/CN=rabbitmq.confirmation.svc.cluster.local/O=ThomsonReuters/C=AU"

# CSR with SANs (required for Kubernetes — multiple DNS names)
openssl req -new -key server.key -out server.csr \
  -subj "/CN=confirmation-rabbitmq-ci" \
  -addext "subjectAltName=DNS:confirmation-rabbitmq-ci,\
DNS:confirmation-rabbitmq-ci.207804-rabbitmq-ci,\
DNS:confirmation-rabbitmq-ci.207804-rabbitmq-ci.svc,\
DNS:confirmation-rabbitmq-ci.207804-rabbitmq-ci.svc.cluster.local"

    What's inside a CSR? Your public key (derived from private key), the domain name(s) you want, your organisation info, and a digital signature proving you own the private key. The CA only needs the CSR — it never sees your private key.

  • 3
    CA Signs the CSR → Issues the Certificate

    You send the CSR to the CA. The CA verifies your identity, signs it with its own private key, and returns your leaf certificate.

    Option A — You ARE the CA (Self-Signed setup like RabbitMQ)

    bash# First, create your own CA (one-time setup)
openssl genrsa -out ca.key 2048
openssl req -x509 -new -nodes -key ca.key -sha256 -days 3650 \
  -out cacert.pem -subj "/CN=TR-Internal-CA/O=ThomsonReuters"

# Now sign your server's CSR with your CA
openssl x509 -req -in server.csr \
  -CA cacert.pem -CAkey ca.key \
  -CAcreateserial -out server.crt \
  -days 365 -sha256 \
  -extfile <(printf "subjectAltName=DNS:confirmation-rabbitmq-ci,\
DNS:confirmation-rabbitmq-ci.207804-rabbitmq-ci,\
DNS:confirmation-rabbitmq-ci.207804-rabbitmq-ci.svc,\
DNS:confirmation-rabbitmq-ci.207804-rabbitmq-ci.svc.cluster.local")

    Option B — External CA (Let's Encrypt / DigiCert)

    bash# Send CSR to Let's Encrypt (via certbot / cert-manager)
# They verify domain ownership, then return a signed cert
# You never manage a Root CA yourself in this case

    In Kubernetes environments — Use cert-manager (Section 19.8) to automate all of this. Manually running openssl is only for understanding the underlying process or for bootstrapping internal CAs.

  • 4
    Build the CA Bundle

    The CA bundle chains the intermediate CA and root CA certificates together. You distribute this to all clients so they can verify the leaf certificate's trust chain.

cat intermediate.crt root.crt > ca-bundle.crt

    TLS Handshake — How It All Comes Together

    Your server now has three files. When a client connects, this is what happens:

RabbitMQ — Our Self-Signed TLS Setup at TR

RabbitMQ at Thomson Reuters uses self-signed TLS certificates — not a public CA, not Istio mTLS. The reason: RabbitMQ runs with the Istio sidecar disabled (AMQP is a binary protocol Envoy can't proxy), so it manages its own TLS independently.

Why Self-Signed?

No public DNS
RabbitMQ is internal to the cluster — only reachable via Kubernetes DNS. Public CAs like Let's Encrypt require public domain validation.
No Istio mTLS
RabbitMQ has sidecar.istio.io/inject: "false" because Envoy can't handle the AMQP binary protocol or Erlang cluster distribution.
Full control
We control cert validity, SANs, rotation schedule. No dependency on external CA availability.
Cost
Public CAs cost money for wildcard/internal certs. Internal CA is free and sufficient for internal cluster traffic.

Why 4 SANs?

Kubernetes services can be reached by multiple DNS forms depending on which namespace the caller is in. A .NET service in the same namespace uses the short name. A service in a different namespace uses the namespace-qualified name. Some configs use the full FQDN. Modern TLS completely ignores the CN field — it only validates SANs. If a .NET service connects using confirmation-rabbitmq-ci.207804-rabbitmq-ci.svc.cluster.local but the cert only has the short name in SANs, the TLS handshake fails with "certificate is valid for confirmation-rabbitmq-ci, not confirmation-rabbitmq-ci.207804-rabbitmq-ci.svc.cluster.local." So we include all 4 forms.
SAN FormUsed by
confirmation-rabbitmq-ciServices in the same namespace (short name resolution)
confirmation-rabbitmq-ci.207804-rabbitmq-ciServices in different namespaces (namespace-qualified)
confirmation-rabbitmq-ci.207804-rabbitmq-ci.svcSome client libraries add .svc automatically
confirmation-rabbitmq-ci.207804-rabbitmq-ci.svc.cluster.localFully qualified Kubernetes DNS (FQDN) — always works

How .NET Services Trust the Self-Signed CA

Out of the box, .NET doesn't trust our internal CA because it's not in the OS certificate store (unlike DigiCert or Let's Encrypt which are pre-trusted everywhere). We solve this in two ways:

Method 1 — Mount CA cert + configure RabbitMQ client

yaml — Helm values / pod spec# ExternalSecret fetches cacert.pem from AWS Secrets Manager
# and makes it available as a volume in every .NET service pod
volumes:
  - name: rabbitmq-ca
    secret:
      secretName: confirmation-rabbitmq-tls-cert
      items:
        - key: ca.crt
          path: ca.crt

volumeMounts:
  - name: rabbitmq-ca
    mountPath: /etc/ssl/rabbitmq
    readOnly: true
C# — RabbitMQ client configurationvar factory = new ConnectionFactory
{
    HostName = "confirmation-rabbitmq-ci.207804-rabbitmq-ci.svc.cluster.local",
    Port = 5671,
    Ssl = new SslOption
    {
        Enabled = true,
        ServerName = "confirmation-rabbitmq-ci",
        CertPath = "/etc/ssl/rabbitmq/ca.crt",   // our CA cert
        AcceptablePolicyErrors = SslPolicyErrors.None
    }
};

Method 2 — Inject CA into OS trust store at container startup

Dockerfile / initContainer# Add our CA to the OS-level trust store
# Then .NET uses it automatically — no code changes needed
COPY cacert.pem /usr/local/share/ca-certificates/tr-internal-ca.crt
RUN update-ca-certificates

Which method do we use at TR? The ExternalSecret + volume mount approach (Method 1). It keeps the CA cert centralised in AWS Secrets Manager and doesn't require rebuilding Docker images when the CA cert rotates.

CA Bundle Injection via ArgoCD PreSync Hooks

The CA certificate must exist in the namespace before any service tries to connect to RabbitMQ. If you deploy a .NET service before the CA cert Secret exists, the pod starts, tries to connect to RabbitMQ, fails cert validation, and crashes. ArgoCD sync waves solve this ordering problem.

yaml — ExternalSecret with sync wave annotationapiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: confirmation-rabbitmq-tls-cert
  annotations:
    argocd.argoproj.io/sync-wave: "-2"   # runs before everything else
spec:
  refreshInterval: 1h

    name: a207804-cn-aws

    name: confirmation-rabbitmq-tls-cert

      remoteRef:
        key: a207804-rabbitmq-ci-tls

    - secretKey: tls.key
      remoteRef:
        key: a207804-rabbitmq-ci-tls

      remoteRef:
        key: a207804-rabbitmq-ci-tls
        property: cacert
"I onboarded RabbitMQ with self-signed TLS using ArgoCD PreSync hooks to inject the CA bundle. The key insight was ordering — the CA cert Secret has to exist before the RabbitMQ cluster CR and before any consumer service deploys. I used sync wave -2 for the ExternalSecret, wave 0 for RabbitMQ, and wave 1 for the .NET services. Without this ordering, services would start with no CA cert to validate against and fail immediately."

Istio & SPIFFE — Automatic mTLS Certificates

For services inside the Istio mesh, you never run openssl manually. Istiod acts as the CA and automatically issues certificates to every Envoy sidecar using the SPIFFE (Secure Production Identity Framework For Everyone) standard.

SPIFFE Identity Format
spiffe://cluster.local/ns/{namespace}/sa/{service-account}

Every pod gets a unique cryptographic identity based on its Kubernetes ServiceAccount — not its IP or hostname.
Auto-Rotation
Istiod rotates all sidecar certificates every 24 hours by default with zero pod restarts. No manual intervention needed.
Istiod = the CA
Istiod maintains an internal Root CA. When a pod starts, the sidecar requests a cert from Istiod using the pod's ServiceAccount token as proof of identity.
AuthorizationPolicy
Because every pod has a SPIFFE identity, you can write policies like "only pods with identity .../sa/istio-ingressgateway can call pricing-be."
sequenceDiagram participant P as New Pod (pricing-be) participant K as Kubernetes API participant I as Istiod (CA) participant S as Envoy Sidecar P->>K: Pod starts, gets ServiceAccount token S->>I: Certificate Signing Request + ServiceAccount token I->>K: Verify ServiceAccount token K-->>I: ✅ Token valid (this is pricing-be in confirmation-ci ns) I->>S: Issue X.509 cert with SPIFFE SAN:\nspiffe://cluster.local/ns/207804-confirmation-ci/sa/pricing-be S->>S: Store cert in memory (not on disk) Note over S: Cert rotates every 24h automatically

cert-manager — Automating Certificate Lifecycle in K8s

cert-manager is the Kubernetes-native way to automate all the manual openssl steps above. It handles issuance, renewal, and secret management automatically.

yaml — cert-manager Certificate resource# Define an Issuer (your internal CA)
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: tr-internal-ca
spec:
  ca:
    secretName: tr-root-ca-secret   # K8s secret containing cacert.pem + key.pem

---
# Request a certificate — cert-manager does all the openssl steps automatically
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: rabbitmq-tls
  namespace: 207804-rabbitmq-ci
spec:
  secretName: confirmation-rabbitmq-tls-cert
  duration: 8760h     # 1 year
  renewBefore: 720h   # renew 30 days before expiry
  issuerRef:
    name: tr-internal-ca
    kind: ClusterIssuer
  dnsNames:
    - confirmation-rabbitmq-ci
    - confirmation-rabbitmq-ci.207804-rabbitmq-ci
    - confirmation-rabbitmq-ci.207804-rabbitmq-ci.svc
    - confirmation-rabbitmq-ci.207804-rabbitmq-ci.svc.cluster.local

cert-manager handles: Private key generation → CSR creation → CA signing → storing the cert in a K8s Secret → automatic renewal before expiry → updating the Secret (which Kubernetes propagates to mounted volumes automatically). You never run openssl again.

Interview Scenarios & Answers

Q: "What is a CA bundle and why do you need it?"
"A CA bundle is a file containing the chain of CA certificates — root and any intermediate CAs — that a client uses to verify a server's certificate. When a server presents its leaf certificate, the client checks whether it was signed by a CA it trusts. Without the CA bundle, the client has nothing to verify against and rejects the connection with 'certificate signed by unknown authority.' At TR, when I set up RabbitMQ TLS, I distributed our internal CA certificate to every .NET service via ExternalSecret. Each service mounts it and uses it to verify RabbitMQ's certificate during the TLS handshake."
Q: "Walk me through how you set up RabbitMQ TLS at TR."
"RabbitMQ at TR uses self-signed certificates because it's internal to the cluster and can't use Istio mTLS — the Envoy sidecar can't handle AMQP binary protocol. I wrote a shell script using openssl to: generate a CA key pair, create a self-signed CA certificate, generate a server key and CSR with 4 SANs covering all Kubernetes DNS forms of the service, sign the server cert with our CA, and create a Kubernetes TLS Secret with the cert, server key, and CA cert. I stored the outputs in AWS Secrets Manager and used ExternalSecret to sync them into the cluster. The CA bundle is then mounted into every .NET service that connects to RabbitMQ. I used ArgoCD sync waves to ensure the Secret exists before any service tries to connect."
Q: "Why did you need 4 SANs in your RabbitMQ certificate?"
"Modern TLS ignores the CN field entirely — it only checks Subject Alternative Names. Kubernetes services can be reached by multiple DNS forms: the short name within the same namespace, the namespace-qualified name from other namespaces, and the full FQDN. Different .NET services and environments were connecting using different forms. If the cert only listed one form and a client connected using a different form, the TLS handshake would fail with a hostname mismatch error even though the cert is valid. So I included all four DNS forms as SANs to cover every possible way a client might resolve and connect to RabbitMQ."
Q: "What is the difference between TLS and mTLS?"
"In regular TLS — which is what HTTPS and our RabbitMQ setup uses — only the server presents a certificate. The client verifies the server's identity but the server doesn't verify the client. In mTLS, both sides present certificates and verify each other. This is what Istio implements between all sidecars in the mesh. The benefit of mTLS is zero-trust — every service proves its identity cryptographically before any traffic is allowed. Combined with AuthorizationPolicy, you can enforce that only specific services with known SPIFFE identities can call each other, regardless of network-level controls."
Q: "A .NET service is getting 'certificate signed by unknown authority' when connecting to RabbitMQ. How do you debug it?"
"First I check whether the CA certificate is actually mounted in the pod: kubectl exec -it <pod> -- ls /etc/ssl/rabbitmq/. If the file is missing, the ExternalSecret or volume mount is misconfigured. If it's there, I verify the cert is valid: openssl verify -CAfile /etc/ssl/rabbitmq/ca.crt /path/to/server.crt. I also check the SANs on the server cert match the hostname the .NET client is using to connect: openssl s_client -connect rabbitmq-host:5671 | openssl x509 -text -noout | grep -A5 SAN. Common causes are: wrong CA cert mounted, SAN mismatch between what the client connects to and what's in the cert, or the cert has expired."
Q: "The RabbitMQ certificate expires in 2 days. How do you rotate it with zero downtime?"
"If using cert-manager, it auto-renews — no action needed. If using our manual script approach: regenerate the cert using the same CA, update the Kubernetes Secret (kubectl create secret generic ... --dry-run=client -o yaml | kubectl apply -f -), and update the value in AWS Secrets Manager. The ExternalSecret will re-sync within its refresh interval. RabbitMQ picks up the new cert on its next restart — so I'd do a rolling restart of RabbitMQ pods. For .NET services, they don't need to restart because they re-read the CA bundle from the mounted volume on each new connection. The key lesson I learned: set up cert expiry monitoring — add a Datadog check on cert expiry dates so you get alerted 30 days out, not 2 days out."
